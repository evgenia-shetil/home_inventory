# Домашній трекер запасів — дизайн

Дата: 2026-09-23
Статус: затверджено до написання плану реалізації

## 1. Задача

Замінити ведення домашніх запасів у Telegram-групі окремим застосунком. У Telegram не працювало головне: старі повідомлення не редагуються, а оновлення кількості через реплаї незручне.

Ключова вимога до UX — оновлення кількості в один тап з телефону.

## 2. Рішення на рівні продукту

Веб-застосунок (PWA), який встановлюється на телефон через «Додати на головний екран». Нативні застосунки і магазини додатків свідомо не використовуються: для персонального інструмента це надлишкові витрати часу й грошей.

### Прийняті обмеження

| Питання | Рішення |
|---|---|
| Користувачі | Одна користувачка, кілька пристроїв (телефон + ноут) |
| Синхронізація | Supabase (Postgres + Storage + Auth) |
| Модель кількості | Число + одиниця виміру (шт / кг / л / пачка) |
| Робота без мережі | Не потрібна, застосунок завжди онлайн |
| Хостинг | GitHub Pages, деплой через GitHub Actions |

### Обсяг першої версії

Входить: картки товарів з фото, кнопка «−1», форма поповнення, сортування за «закінчується», журнал операцій, категорії, список покупок.

Не входить: довільні пункти у списку покупок, сканування штрихкодів, сповіщення, прогноз «скоро закінчиться», робота офлайн.

Прогноз навмисно відкладено: він потребує накопиченої історії за кілька місяців, тож на порожньому журналі не має сенсу. Журнал у першій версії закладається саме для того, щоб ці дані почали збиратись з першого дня.

## 3. Архітектура

Статичний фронтенд спілкується з Supabase напряму. Власного серверного коду немає — його нема де виконувати, бо GitHub Pages віддає лише файли.

```
Браузер (React SPA, PWA)
   |
   |-- supabase-js
   v
Supabase
   ├── Postgres  (categories, items, events + RPC adjust_quantity)
   ├── Storage   (приватний бакет photos)
   └── Auth      (magic link на email)
```

Наслідок такої архітектури: жодна логіка на клієнті не може вважатись довіреною. Усі правила доступу і цілісності живуть у базі — у RLS-політиках і в RPC-функції.

### Стек

- React + Vite
- `@supabase/supabase-js`
- Хеш-роутинг (через підпапку на GitHub Pages)
- `base` у конфізі Vite = назва репозиторію

## 4. Модель даних

### categories

| Поле | Тип | Опис |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK → auth.users | |
| name | text NOT NULL | |
| sort_order | int DEFAULT 0 | Порядок у стрічці категорій |
| created_at | timestamptz | |

### items

| Поле | Тип | Опис |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK → auth.users | |
| name | text NOT NULL | |
| category_id | uuid FK → categories, NULL | Товар без категорії допустимий |
| photo_path | text NULL | Шлях у Storage, не сам файл |
| qty | numeric NOT NULL DEFAULT 0 | Поточна кількість |
| unit | text NOT NULL DEFAULT 'шт' | Одиниця виміру |
| threshold | numeric NOT NULL DEFAULT 1 | Поріг «закінчується», свій у кожного товару |
| last_price | numeric NULL | Ціна за одиницю з останнього поповнення |
| last_place | text NULL | Де куплено востаннє |
| created_at, updated_at | timestamptz | |

`threshold` зберігається на рівні товару, а не глобально: два рулони паперу означають «пора купувати», а дві пачки солі — піврічний запас.

### events

| Поле | Тип | Опис |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK → auth.users | |
| item_id | uuid FK → items ON DELETE CASCADE | |
| delta | numeric NOT NULL | −1 витрата, +N поповнення |
| kind | text NOT NULL | `consume` / `restock` / `correction` |
| price | numeric NULL | Ціна за одиницю, лише для `restock` |
| place | text NULL | |
| created_at | timestamptz DEFAULT now() | |

Числові поля — `numeric`, не число з рухомою комою: дробові типи зберігають значення наближено і накопичують похибку на цінах.

### Список покупок

Окремої таблиці немає. Список покупок — це вибірка з `items`, де `qty <= threshold`. Зберігати «закінчується» окремо означало б дублювати той самий факт у двох місцях із ризиком розходження.

## 5. Зміна кількості

Усі зміни кількості проходять через одну функцію в базі:

```
adjust_quantity(item_id, delta, kind, price?, place?)
```

Виклики:

| Дія | Параметри |
|---|---|
| Тап «−1» | `delta = -1, kind = 'consume'` |
| Поповнення | `delta = +N, kind = 'restock'`, опційно `price`, `place` |
| Виправлення / скасування | `delta = ±N, kind = 'correction'` |

Функція однією транзакцією оновлює `items.qty` і вставляє рядок у `events`. Атомарність тут обов'язкова: якби клієнт робив два окремі запити, втрата другого залишила б дірку в журналі, і прогноз будувався б на неповних даних.

Правила всередині функції:

- кількість не опускається нижче нуля;
- `restock` з переданою ціною оновлює `last_price`, з переданим місцем — `last_place`;
- `updated_at` оновлюється завжди.

Функція також знімає гонку між пристроями: зміна виконується як `qty = qty - 1` всередині бази, тож два одночасні тапи з телефона й ноута дають −2, а не −1.

Прямий `UPDATE` поля `qty` з клієнта заборонено політикою — щоб не існувало способу змінити кількість повз журнал.

## 6. Безпека

**Автентифікація:** magic link на email. Паролів немає. Сесія зберігається на пристрої й оновлюється у фоні.

**RLS** увімкнено на всіх трьох таблицях, правило `user_id = auth.uid()` на читання, вставку, оновлення й видалення.

**Storage:** приватний бакет `photos`, шлях `{user_id}/{item_id}.jpg`, політика доступу за тим самим принципом.

**Ключі:** у фронтенд потрапляє лише `anon key`. Він публічний за задумом і прав сам по собі не дає — доступ визначають RLS і те, хто залогінений. `service_role` key у фронтенді не використовується ніде і ніколи: він обходить RLS повністю.

**Перевірка перед першим деплоєм:** запит до кожної таблиці з публічним ключем без логіна. Очікуваний результат — порожня відповідь.

## 7. Екрани

Навігація — нижня панель на два пункти (Запаси / Покупки). Нижня, бо великий палець дістає низ екрана, а не верх.

### Запаси

Сітка карток у дві колонки: фото, назва, кількість з одиницею. Кнопка «−1» на всю ширину картки — велика ціль, щоб влучати не дивлячись. Зверху горизонтальна стрічка категорій, за замовчуванням «усі».

Сортування єдине, без перемикача: спершу те, що на межі. Ранжування за відношенням `qty / threshold`, а не за абсолютною кількістю — інакше товар з порогом 10 і залишком 4 виглядав би благополучнішим за той, де залишилась одна одиниця з однієї.

### Картка товару

Відкривається тапом по фото або назві (не по кнопці «−1»). Містить: форму поповнення (кількість, опційно нова ціна й місце), редагування полів, журнал операцій, видалення. Ціна показується двома числами — за одиницю і загальна вартість залишку.

### Покупки

Товари нижче порога у вигляді чекліста. Відмітка «купила» відкриває ту саму форму поповнення.

### Додавання товару

Фото з камери, назва, категорія, кількість, одиниця, поріг, ціна, місце. Обов'язкові — лише назва і кількість.

### Вхід

Поле email і кнопка. Після переходу за посиланням з листа — повернення на екран, з якого починався вхід.

## 8. Взаємодія і стани

### Оптимістичне оновлення

Тап «−1» зменшує число на екрані негайно, до відповіді сервера, і показує плашку «Витрачено 1 · Скасувати» на 5 секунд.

Відкат при помилці виконується як **зворотна зміна** (`+1`), а не як повернення до запам'ятованого значення. Інакше другий тап, що встиг пройти за ці півсекунди, був би затертий.

«Скасувати» не стирає подію з журналу, а додає компенсуючу з типом `correction`. Історія лишається правдивою: видно помилковий тап і виправлення.

### Стани списків

- Завантаження — скелетони карток, не спінер посеред порожнього екрана
- Порожньо — для нового акаунта кнопка «додати перший товар»; порожній список покупок оформлюється як добра новина, а не як помилка
- Помилка — текст і «спробувати ще»

### Мережа

Якщо запит не проходить — плашка «немає зв'язку» і автоматична повторна спроба, коли браузер повідомить про відновлення мережі. Невдала дія відкочується, а не зависає.

### Сесія

Протермінований токен оновлюється у фоні. Екран входу показується лише якщо оновити не вдалось, з поверненням на попередній екран після входу.

### Фото

Завантаження в Storage — окремий крок після створення товару. Невдале завантаження не скасовує створення: товар зберігається, картка показує заглушку і кнопку «додати фото».

Знімки стискаються на клієнті через canvas до ~1200 px по довшій стороні і зберігаються як JPEG. Знімок з телефону важить 3–4 МБ, для картки достатньо 100–150 КБ — різниця у швидкості відкриття списку на мобільному інтернеті вимірюється десятками разів.

## 9. PWA

Маніфест, іконка, повноекранний режим, встановлення через «На головний екран».

Особливості iOS, які треба врахувати:

- встановлювати можна лише з Safari; в інших браузерах пункт відсутній або створює звичайний ярлик;
- система має право витерти локальні дані застосунку після тривалого простою. Для нас це не критично, бо дані живуть у Supabase — наслідком буде максимум повторний вхід.

## 10. Деплой

GitHub Actions збирає проєкт і публікує на Pages при кожному пуші в `main`.

Особливості GitHub Pages, закладені з самого початку:

- сайт живе в підпапці `/<назва-репо>/`, тому в конфіг Vite прописується `base`;
- маршрутизація через хеш, інакше пряме відкриття будь-якої сторінки, крім головної, дає 404.

## 11. Тестування

Покривається логіка, де помилка не видна одразу:

- `adjust_quantity` — не йде в мінус, пише подію, оновлює `last_price` і `last_place`;
- сортування за «закінчується» — коректне ранжування за відношенням до порога;
- відкат оптимістичного оновлення — зворотна зміна не затирає паралельний тап.

Верстка тестами не покривається: для персонального застосунку такі тести коштують дорожче, ніж дають.
