# Запаси — контекст проєкту

PWA для обліку домашніх запасів. Одна користувачка, кілька пристроїв.
Головна вимога до UX: оновити кількість одним тапом з телефону.

- Прод: https://evgenia-shetil.github.io/home_inventory/
- Дизайн: `docs/superpowers/specs/2026-09-23-home-inventory-design.md`
- План реалізації: `docs/superpowers/plans/2026-09-23-home-inventory.md`

## Архітектура

Статичний React-фронтенд ходить у Supabase напряму. Власного серверного коду
немає і бути не може: GitHub Pages віддає лише файли.

```
Браузер (React SPA, PWA) → supabase-js → Supabase
                                          ├── Postgres (categories, items, events + RPC)
                                          ├── Storage (приватний бакет photos)
                                          └── Auth (пароль, magic link запасний)
```

Наслідок: **жодна логіка на клієнті не є довіреною.** Усі правила цілісності
й доступу живуть у базі.

## Інваріанти — ламати не можна

1. **Кількість змінюється тільки через `adjust_quantity`.** Функція однією
   транзакцією оновлює `items.qty` і пише рядок у `events`. Прямий `UPDATE`
   стовпця `qty` заборонений на рівні column grants (`0002_rls.sql`), бо RLS
   не вміє обмежувати окремі стовпці. Якщо знадобиться новий вид операції —
   додавати `kind`, а не обхідний шлях.

2. **RLS увімкнена на всіх таблицях**, правило `user_id = auth.uid()`.
   Перевірка перед деплоєм: `node --env-file=.env scripts/verify-rls.mjs`,
   має вивести три `ok`. Порожня успішна відповідь аноніму — це правильно;
   помилка доступу або непорожній список — ознака поломки.

3. **`service_role` ключ не використовується ніде.** У фронтенд іде лише
   публічний `sb_publishable_...`, він за задумом видимий у коді сторінки.
   Захищає не таємність ключа, а RLS і логін.

4. **Грошові й кількісні поля — `numeric`**, ніколи `float`.

5. **Штрихкод унікальний у межах користувача** (частковий індекс
   `items_barcode_uniq`, лише для непорожніх). Порушення приходить кодом
   `23505` — його треба показувати людською фразою, а не текстом Postgres.

6. **Список покупок не має власної таблиці.** Це вибірка з груп, у яких
   сума нижча за поріг. Заводити для нього сутність означало б зберігати
   той самий факт двічі.

7. **Запас вимірюється потребою, а не маркою.** Поріг «закінчується» живе
   на КАТЕГОРІЇ (`categories.threshold`), а не на товарі: чотири різні
   зубні щітки — це один запас із чотирьох одиниць, і сигнал має прийти,
   коли їх сумарно лишиться мало. Групування й поріг рахує
   `src/domain/groups.js`. `items.threshold` лишився тільки як запасний
   поріг для товарів поза категоріями і з форми прибраний.

## Граблі, на які вже наступили

**Оптимістичне оновлення не є сигналом «сервер відповів».** Кількість
змінюється двічі: спершу оптимістично, до запиту, потім приходить
підтвердження з тим самим числом. Тому ефекти, яким потрібні свіжі серверні
дані (як історія операцій в `ItemScreen`), залежать від `updated_at`, а не
від `qty`. Інакше запит летить раніше, ніж подія потрапить у базу, а другого
спрацювання не буде — значення ж не змінилось.

**Відкат робиться зворотною зміною, а не поверненням знімка.** `applyDelta`
повертає фактично застосовану дельту саме для цього: відкотити треба її, бо
паралельний тап, що встиг пройти, інакше буде затертий. Дельта може бути
урізана обмеженням нуля — тоді й відкат нульовий.

**Категорії створюються перед завантаженням, не паралельно.** Виклик
`ensure_default_categories` живе в `InventoryContext`, до `reload()`. Коли він
стояв у `App.jsx` без `await`, при першому вході список читався раніше, ніж
заповнювався, а будь-яка відмова тонула мовчки.

**Бакет приватний — `getPublicUrl()` дасть 403.** Посилання на фото підписані
й живуть годину, кеш у `src/lib/photos.js`. Після перезавантаження фото шлях
не змінюється, тож старий підпис треба викидати через `invalidatePhoto`.

**Схема бази їде поперед коду.** Міграція, що додає стовпець, застосовується
ДО пуша коду, який на нього розраховує. У зворотному порядку між деплоєм і
міграцією застосунок зламаний: Postgres відповідає, що стовпця не існує.
Так було з `barcode` — код закомічений локально, запушений після міграції.

**Бібліотека розпізнавання штрихкодів вантажиться лениво.** `@zxing/browser`
підвантажується динамічним import лише на екрані сканера й потрапляє в
окремий чанк (~125 КБ стиснуто). Статичний import зіпсував би завантаження
головного екрана заради функції, якою користуються зрідка. На Android є
вбудований `BarcodeDetector` — там бібліотека взагалі не потрібна, тож
спершу перевіряється він.

**GitHub Pages віддає сайт із підпапки.** Тому в `vite.config.js` стоїть
`base: '/home_inventory/'`, а роутер — **тільки** `HashRouter`. З
`BrowserRouter` пряме відкриття будь-якої сторінки, крім головної, дасть 404.

## Команди

```
npm run dev      # локальний сервер на /home_inventory/
npm test         # юніт-тести (чиста логіка)
npm run build
node --env-file=.env scripts/verify-rls.mjs   # перевірка доступу
node scripts/make-icons.mjs                   # перегенерувати іконки
```

Інтеграційні тести проти живої бази вимагають `TEST_EMAIL` і `TEST_PASSWORD`
у `.env`; без них вони пропускаються, а не падають:

```
npx vitest run tests/integration
```

## Міграції

`supabase/migrations/` виконуються вручну в Supabase SQL Editor по порядку
номерів. `supabase/apply-all.sql` — склейка 0001-0004 для вставки одним
шматком. `0005_storage.sql` застосовується **після** створення бакета
`photos` (приватного) у панелі Storage.

## Деплой

Пуш у `main` → GitHub Actions → Pages. Спершу `npm test`: якщо тести впали,
деплою не буде і на проді лишиться попередня робоча версія.

Ключі потрапляють у збірку зі секретів репозиторію `VITE_SUPABASE_URL` і
`VITE_SUPABASE_ANON_KEY` (Settings → Secrets and variables → Actions).

## Експлуатація

**Основний спосіб входу — пошта і пароль**, не magic link. Вбудована пошта
Supabase має жорсткий ліміт (одиниці листів на годину на безкоштовному
тарифі), через який вхід впирався в `email rate limit exceeded`. Magic link
лишився запасним шляхом на екрані входу, для забутого пароля.

Пароль міняється в самому застосунку: розділ «Ще» → Пароль. Там же вихід
з акаунта.

**Реєстрація нових користувачів вимкнена** (Authentication → Sign In /
Providers → User Signups). Існуючі акаунти входять нормально. Щоб створити
новий акаунт, робити це в панелі: Authentication → Users → Add user →
Create new user, з паролем і авто-підтвердженням. Самостійна реєстрація з
застосунку дасть `Signups not allowed for this instance`.

**Тестовий акаунт `test@example.com`** входить лише паролем: magic link на
нього не працює, бо Supabase вважає домен `example.com` недійсним для листів.

**Безкоштовний проєкт Supabase паузиться після 7 днів без звернень.**
Будиться кнопкою в панелі.

## Структура екранів

Головний екран — перелік ПОТРЕБ, а не товарів: стрічка головних категорій
зверху, нижче рядки підкатегорій із підсумковою кількістю. Марки всередині
відкриваються окремим екраном `/category/:id`. Так зроблено тому, що поріг
тепер рахується по групі — на головній видно саме те, що він вимірює.

Товар без категорії показується на головній як власна група і веде прямо
на свою картку.

## Категорії

Дерево через самопосилання `categories.parent_id`, глибина 2. Одні й ті
самі операції працюють на обох рівнях, тому редагування написане один раз
(`/categories`, доступне з «Ще»).

Унікальність назви — В МЕЖАХ БАТЬКА, не глобальна: «крем» під «обличчям»
і під «тілом» це різні речі. Потрібні два часткові індекси, бо для
кореневих батька немає, а NULL Postgres вважає унікальним сам по собі
і від дублів не захистить.

`ensure_default_categories` сидить набір лише для ПОРОЖНЬОГО акаунта.
Раніше вона працювала щоразу й «воскрешала» видалені категорії.

Категорію нового товару застосунок пробує визначити сам за назвою
(`src/domain/suggest.js`, словник ключових слів). Щойно категорію обрали
руками, підказка замовкає.

## Магазини

Окремої таблиці немає: список збирається з уже введених `items.last_place`
плюс кілька стартових назв (`src/domain/places.js`). Магазин не має
самостійного життя — це лише мітка на покупці, на відміну від категорії,
яка існує і порожньою.

## Штрихкоди

Два незалежні механізми, які легко переплутати:

1. **Упізнавання свого товару** — звірка з `items.barcode`. Працює завжди,
   жодних зовнішніх залежностей. Це основна цінність сканера: списати або
   поповнити наявний товар одним наведенням камери.

2. **Пошук назви й фото в каталогах** Open Beauty / Products / Food Facts
   (`src/domain/lookup.js`). Безкоштовно, без ключів, CORS дозволений і для
   API, і для картинок. Але покриття нерівне: харчові товари є майже всі,
   побутова хімія й косметика — як пощастить. Корисно рівно один раз, при
   першому додаванні товару, тому відсутність знахідки не є помилкою —
   форма просто заповнюється вручну.

Контрольна цифра EAN перевіряється до походу в мережу (`isValidBarcode`):
неповний скан не має коштувати трьох марних запитів.

## Свідомо поза обсягом

Прогноз «скоро закінчиться» (журнал накопичує дані з 2026-09-23, за кілька
місяців буде на чому будувати), редагування категорій з інтерфейсу, довільні
пункти у списку покупок, робота офлайн, імпорт історії з Telegram
(відмовились свідомо: він дав би назви без штрихкодів, а сканувати все одно
довелося б).

## Стиль

Мова інтерфейсу, комітів і коментарів — українська. Числівники проганяти
через `plural()` з `src/lib/plural.js`: українська має три форми, і 11-14
є винятком попри останню цифру. Коментарі пояснюють
*чому*, а не *що*: код видно, а причину рішення — ні.
